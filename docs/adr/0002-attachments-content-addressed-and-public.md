# Attachments are content-addressed and public, and their original filename is dropped

The `ATTACHMENT` data type stores files of any type (max 10 MB) like photos: under `<sha256>.<ext>` (full hash) in `text_value`, publicly downloadable by anyone who knows the hash. The original filename is deliberately not stored. This avoids filename conflicts, a second column and a lookup at download time. Download names are generated by the frontend as `<attribute>_<entity>_<date>.<ext>`.

## Consequences

- Leaked attachment URLs stay valid forever, as with photos. This was accepted in favour of consistency with photos and simplicity.
- Because any file type is accepted and served from our own origin, the download endpoint must not let the browser render active content (stored XSS). Only an allowlist is served inline with its exact `Content-Type` (`pdf`, `png`, `jpg/jpeg`, `gif`, `webp`, `avif`, `txt`, `mp4`, `webm`, `mp3`, `wav`, `ogg`). Everything else, including `csv`, `html` and `svg`, is sent as `Content-Disposition: attachment` with `application/octet-stream`. `X-Content-Type-Options: nosniff` is always set. Do not widen the allowlist to types that can run scripts.
- `Content-Security-Policy: sandbox` was not used for this, because Chrome refuses to render PDFs under it.
